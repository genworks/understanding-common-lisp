\chapter{Interfaces}

A program has to deal with the world outside it: the operating system,
code written in other languages, the network, databases, the web. The
Common Lisp standard covers files and streams and stops there. The
rest is done by libraries, and for each job there is a well-established
portable one that works the same on every implementation. This
chapter introduces the ones you are likely to need first.

Each is loaded with Quicklisp, as described in Chapter~2. For
example:

\begin{verbatim}
CL-USER> (ql:quickload "cffi")
\end{verbatim}

\noindent
The examples below assume you have loaded the library named in each
section. The commercial implementations also have interfaces of their
own for most of these things, described in their manuals.

\section{The Operating System}

UIOP\index{UIOP} is a library of portable utilities for dealing with the
operating system. It is part of ASDF, so it is already there. Its
\code{run-program}\index{run-program@\texttt{run-program}} runs another program and can return what it
printed:

\begin{verbatim}
CL-USER> (uiop:run-program '("date" "+%Y")
                           :output '(:string :stripped t))
"2026"
NIL
0
\end{verbatim}

The three values are the program's output, its error output, which was
not collected here, and its exit code. Giving the command as a list
of strings, as above, passes the arguments straight to the program.
You can also give one string, which is handed to the shell.

Environment variables are read with \code{uiop:getenv}\index{environment variables}, which returns
\code{nil} if the variable is not set:

\begin{verbatim}
CL-USER> (uiop:getenv "HOME")
"/home/reader"
\end{verbatim}

UIOP also has functions for the file system, such as
\code{directory-files}, \code{copy-file}, \code{ensure-directories-exist}
and \code{read-file-string}. Where a Lisp function will do the job,
prefer it to running a shell command: it works the same on every
operating system, and when it fails you get a Lisp condition you can
handle.

\section{Foreign Functions}

Most operating systems and a great many libraries present their
interface as C functions. CFFI\index{CFFI}, the Common Foreign Function
Interface (\url{https://cffi.common-lisp.dev}), lets Lisp call
them. The steps are:

\begin{enumerate}
\item Load the shared library that contains the functions (a
\code{.so} file on Linux, \code{.dylib} on macOS, \code{.dll} on
Windows). The C standard library is already loaded.

\item Tell Lisp the name of each function and the types of its
arguments and result.

\item Call it.
\end{enumerate}

For a single call, \code{foreign-funcall} does the last two steps at
once. Here is the C function \code{strlen}:

\begin{verbatim}
CL-USER> (cffi:foreign-funcall "strlen" :string "Hello, C!" :size)
9
\end{verbatim}

The arguments come in pairs of a type and a value, and the type of
the result comes last. To make a C function callable like a Lisp
function, define it once with \code{defcfun}\index{defcfun@\texttt{defcfun}}:

\begin{verbatim}
CL-USER> (cffi:defcfun ("getpid" process-id) :int)
PROCESS-ID
CL-USER> (process-id)
4242
\end{verbatim}

A great many C libraries have already been wrapped this way and are
in Quicklisp, so look there before you write your own.

\section{Threads}

Every current implementation can run several threads\index{threads} at once. Each
has its own functions for this, and the Bordeaux Threads\index{Bordeaux Threads} library puts
one interface over all of them. Its current interface is in the
package \code{bt2}:

\begin{verbatim}
(defparameter *counter* 0)
(defparameter *lock* (bt2:make-lock))

(defun count-up (times)
  (dotimes (n times)
    (bt2:with-lock-held (*lock*)
      (incf *counter*))))
\end{verbatim}

\begin{verbatim}
CL-USER> (let ((threads (loop repeat 4
                              collect (bt2:make-thread
                                       (lambda () (count-up 100000))))))
           (mapc #'bt2:join-thread threads)
           *counter*)
400000
\end{verbatim}

Four threads each add to the counter a hundred thousand times.
\code{Join-thread} waits for a thread to finish. The lock makes sure
that only one thread changes the counter at a time; without it, some
of the additions would be lost. All the threads share the same
memory, so data that more than one of them changes needs a lock.

A dynamic binding made with \code{let} in one thread, on the other
hand, is seen only by that thread, as Chapter~3 mentioned.

\section{TCP/IP Sockets}

The \code{usocket}\index{usocket} library gives portable access to network
sockets\index{sockets}. A connected socket gives you a stream, and you read and write
it with the same functions as a file.

Here is a server that accepts one connection, reads a line from it,
sends an answer, and closes:

\begin{verbatim}
(defun serve-once (port)
  (let ((listener (usocket:socket-listen "127.0.0.1" port
                                         :reuse-address t)))
    (unwind-protect
         (let* ((connection (usocket:socket-accept listener))
                (stream (usocket:socket-stream connection)))
           (unwind-protect
                (let ((command (read-line stream)))
                  (format stream "You said: ~a~%" command)
                  (finish-output stream))
             (usocket:socket-close connection)))
      (usocket:socket-close listener))))
\end{verbatim}

\noindent
and a client that connects, sends a line, and returns the reply:

\begin{verbatim}
(defun ask (port message)
  (let* ((socket (usocket:socket-connect "127.0.0.1" port))
         (stream (usocket:socket-stream socket)))
    (unwind-protect
         (progn
           (write-line message stream)
           (finish-output stream)
           (read-line stream))
      (usocket:socket-close socket))))
\end{verbatim}

To try them in one Lisp, run the server in a thread of its own, since
it waits for a connection:

\begin{verbatim}
CL-USER> (bt2:make-thread (lambda () (serve-once 4444)))
#<BT2:THREAD "Unknown thread 4" {1206502383}>
CL-USER> (ask 4444 "hello")
"You said: hello"
NIL
\end{verbatim}

They would work just as well in two Lisps on two machines, with the
server's address in place of \code{127.0.0.1}. The calls to
\code{finish-output} matter: output to a socket is buffered, and
nothing is sent until the buffer fills or you ask. The
\code{unwind-protect} forms make sure that the sockets are closed
whatever happens.

A real server would handle many connections and deal with errors.
For the usual protocols you will not write that yourself. The next
sections use libraries built on top of sockets.

\section{JSON}

Much of the data that programs exchange is JSON\index{JSON}. Several libraries
read and write it. One good current choice is \code{jzon}, loaded
as \code{com.inuoe.jzon}. A package name that long is a case for the
local nicknames of Section~\ref{sec:packages}; here we write it out.

\begin{verbatim}
CL-USER> (defparameter *city*
           (com.inuoe.jzon:parse
            "{\"name\": \"Detroit\", \"tags\": [\"motor\", \"music\"]}"))
*CITY*
CL-USER> (gethash "name" *city*)
"Detroit"
T
CL-USER> (gethash "tags" *city*)
#("motor" "music")
T
\end{verbatim}

A JSON object becomes a hash table with string keys, and a JSON array
becomes a vector. \code{Stringify} goes the other way:

\begin{verbatim}
CL-USER> (com.inuoe.jzon:stringify (list 1 2 "three"))
"[1,2,\"three\"]"
\end{verbatim}

\section{Databases}

There are libraries for all the common database\index{databases} systems, among them
Postmodern for PostgreSQL, \code{cl-mysql}, and \code{cl-dbi}, which
gives one interface to several. The simplest to try is SQLite, which
keeps a whole database in one file and needs no server. The Lisp
library is called \code{sqlite}, and it uses the SQLite C library,
which must be installed on your machine.

\begin{verbatim}
CL-USER> (defparameter *db* (sqlite:connect ":memory:"))
*DB*
CL-USER> (sqlite:execute-non-query *db*
           "create table capitals (state text, city text)")
NIL
CL-USER> (sqlite:execute-non-query *db*
           "insert into capitals values (?, ?)" "Michigan" "Lansing")
NIL
CL-USER> (sqlite:execute-non-query *db*
           "insert into capitals values (?, ?)" "Illinois" "Springfield")
NIL
CL-USER> (sqlite:execute-to-list *db*
           "select * from capitals order by state")
(("Illinois" "Springfield") ("Michigan" "Lansing"))
CL-USER> (sqlite:execute-single *db*
           "select city from capitals where state = ?" "Michigan")
"Lansing"
CL-USER> (sqlite:disconnect *db*)
\end{verbatim}

The name \code{":memory:"} asks for a temporary database in memory;
give a file name to keep one on disk. Each row comes back as a list.
Always pass values to a query through the question-mark placeholders,
as here, and never by pasting them into the SQL text. That is what
keeps hostile input from being run as SQL.

\section{Web Serving}

A web server\index{web serving} written in Lisp runs inside your Lisp image. That has a
pleasant consequence: all of the program's state is right there in
memory between requests, and you can redefine the function behind a
page while the server is running and see the change on the next
request.

Hunchentoot\index{Hunchentoot} (\url{https://edicl.github.io/hunchentoot/}) is a
widely used web server library. Start a server on a port:

\begin{verbatim}
CL-USER> (defparameter *server*
           (hunchentoot:start
            (make-instance 'hunchentoot:easy-acceptor :port 8000)))
*SERVER*
\end{verbatim}

\noindent
and define a page:

\begin{verbatim}
(hunchentoot:define-easy-handler (hello :uri "/hello")
    ((name :init-form "World"))
  (setf (hunchentoot:content-type*) "text/plain")
  (format nil "Hello, ~a!" name))
\end{verbatim}

Now visit \url{http://localhost:8000/hello} in your browser and you
will see ``Hello, World!'' The handler is a function. Whatever it
returns is sent to the browser. The parameter \code{name} is filled
in from the request, so \url{http://localhost:8000/hello?name=Lisp}
answers ``Hello, Lisp!'' The same parameter is filled in from a
posted form.

\textbf{Try it:} With the server running, change the greeting in the
handler, evaluate the definition again, and reload the page.

You can make requests from Lisp as well. Dexador and Drakma are HTTP
client libraries:

\begin{verbatim}
CL-USER> (dexador:get "http://localhost:8000/hello?name=Lisp")
"Hello, Lisp!"
200
...
\end{verbatim}

\noindent
The first two values are the body of the response and the HTTP status
code. To stop the server, call \code{(hunchentoot:stop *server*)}.

To produce HTML you can use \code{format}, or better, one of the
libraries that write HTML from Lisp lists, such as Spinneret or
CL-WHO. For larger applications there are frameworks built on these
pieces. Hunchentoot is not the only server: Franz's AllegroServe, used
in the earlier editions of this book, is open source and runs on several
implementations, and Clack and Woo are other popular choices.

\section{Embedded Languages}

Chapter~3 showed that macros let you add operators to Common Lisp.
Carried further, a set of macros and functions becomes a language in
its own right for some kind of problem, sitting on top of CL. This is
called an \emph{embedded language}\index{embedded languages}, or a domain-specific language.
The \code{loop} macro and the HTML libraries just mentioned are small
ones.

A larger example is Gendl\index{Gendl} (\url{https://gendl.org}), an open-source
language for engineering and design applications. Its main operator,
\code{define-object}, is to Gendl what \code{defclass} is to CLOS.
The objects it defines compute their values on demand, remember them,
and keep track of what depends on what, so that when an input changes,
whatever was computed from it is worked out again the next time it is
asked for. A Gendl program is still a Common Lisp program. It is
compiled by the same compiler, loaded with ASDF, and developed at the
same REPL, with all of CL available inside it.

That is the general pattern. Because the embedded language is made of
ordinary macros, it needs no parser, no separate compiler and no
bridge to the host language, and its users keep the whole of Common
Lisp. Building a language up toward the problem, until the program
says what it means in the problem's own terms, is the style of
programming that Lisp was designed for.
